# Найти инструмент, взять и использовать для набора

Решение владельца16.11: расширить сценарий EB300 до поиска подходящего предмета на столе, удобного хвата, подъёма, поиска клавиатуры и физического набора буквы/слова. Общее название — **инструмент для набора на клавиатуре**; первый конкретный объект — карандаш. Доступен также режим нажатия штатной губкой. Старые файлы `pregrasped-rod` сохраняют название/хеши как историю уже выполненного опыта.

Камера остаётся выбранной боковой Redmi 8A на запястье: один полный кадр без zoom/crop/внешних камер. [Существующий fixed-pregrasp preview](2026-11-16-pregrasped-tool-preview.md) доказывает лишь заданный контакт заранее закреплённой палочки с A. Поиск/подбор/хват/удержание этим ещё не реализованы.

## Целевой эпизод и проверяемые результаты

| Фаза | Результат, который нужно получить |
|---|---|
| Осмотреть стол | Из обзорных поз wrist camera найти инструмент; при отсутствии/перекрытии не подменять поиск известной sim-позицией |
| Выбрать хват | Определить ось, рабочий конец и место хвата; проверить доступность, свободный ход губок и стол |
| Подвести захват | Дойти до pregrasp без контактов со столом и посторонними предметами |
| Взять и поднять | Закрыть управляемые губки, поднять свободный предмет и подтвердить удержание |
| Подготовить инструмент | Получить удобную для нажатия ориентацию и оценку tool/TCP относительно захвата |
| Найти клавиатуру | Найти её положение и поддерживаемые клавиши по наблюдениям, согласовать систему координат |
| Набрать | Сначала A, затем несколько клавиш и поддерживаемое слово, например NEWTON; регистрировать нужное нажатие и отпускание |
| Завершить | Проверить фактически набранную строку, затем положить инструмент или перейти к следующей задаче |

## Что означает удобный хват

Предпочтение владельца: ось карандаша близка к **продольному направлению губок**, рабочий конец выступает перед ними и остаётся видимым. «Вертикаль губки» трактуется как её локальное продольное направление, не обязательная вертикаль мира во время подбора. Для нажатия инструмент после подъёма разворачивается концом к поверхности клавиш.

Лежащий на плоскости карандаш и ориентированный вниз инструмент — разные позы. Прямой продольный хват с торца может ограничиваться толщиной пальцев, столом и местом вокруг карандаша. Сначала проверяем его на настоящей геометрии EBG20. Если он недоступен, рассматриваем поддерживаемый готовым решением другой подход/перехват; не обещаем, что любой хват удастся исправить одним вращением запястья. Угол между осями сам по себе не подтверждает устойчивость хвата.

Для первого объекта сохраняем стартовую геометрию из preview: диаметр около8мм, длина около138мм, выступ рабочего конца от центра хвата около65мм; это **номинальный ориентир**, не обязательные размеры всех инструментов. Масса, трение, форма, зазор пальцев, рабочий конец и допустимый выступ задаются отдельно. Численный допуск соосности выбирается после проверки реального раскрытия/контактов, а не объявляется универсальным.

## Необходимые изменения стандартных данных

1. Проверить существующий gripper workflow производителя/поддерживаемой среды. R8 сейчас объединяет элементы захвата на wrist3 с фиксированным раскрытием. Нужно обоснованное описание подвижных узлов/связей, диапазона, привода и контактов. Четырёхзвенник нельзя молча заменить произвольным prismatic joint.
2. Добавить отдельную кандидатную сцену со **свободным** предметом на столе. Для физической приёмки не использовать fixed attachment, teleport или программный weld после объявления «взял».
3. Проверить геометрическую доступность хватов с условно известной позой предмета. Этот диагностический этап явно использует sim ground truth и не называется поиском по зрению.
4. Перейти к camera observations. Скрытые object/key transforms могут использоваться evaluator/teacher по правилам метода, но не подмешиваются в vision policy или «найденный» объект без наблюдения.
5. Подготовить задачи/демонстрации в формате выбранного готового recipe. Контракт текущего NVIDIA typing остаётся шестимерным по руке; добавление gripper action или другой motor model — отдельная явно описанная adaptation, не незаметное расширение config.

## Какой готовый путь исследован

[MoveIt Task Constructor](https://moveit.picknik.ai/main/doc/tutorials/pick_and_place_with_moveit_task_constructor/pick_and_place_with_moveit_task_constructor.html) уже разделяет approach, генерацию grasp pose, IK, close и lift. Прочитан tutorial source `moveit/moveit2_tutorials@4524ccb8edff245ddd7615749975bb035f453ee3`. Это механический/планировочный reference, а не выбранная новая обязательная установка: для EB300 пока нет принятого полного MoveIt/control integration. `attachObject` планировщика описывает занятую геометрию и не доказывает физическое удержание.

Основной typing route сохраняется: `NVIDIA/so101-typing-task@7aec2ed26dce8c88ae007a2714680cce572e1466`, наша разрешённая EB300 adaptation и PPO teacher→vision. Готовые VLA/WAM рассматриваются как отдельный возможный backend для манипуляции, после проверки релиза и совместимости. [GR00T2, доступные модели и граница zero-shot](<../../../../../../_ПЛАНЫ_/embedded-robotics-market-research/research/projects/robohand/foundation-models-and-tool-use-2026-11-16.md>).

## Порядок следующих gates

| Gate | Что принимаем |
|---|---|
| G1 — gripper | Управляемое открытие/закрытие на достоверной кинематике; контакты/диапазоны; сохранённая исходная R8 |
| G2 — хват | Свободный карандаш: подвод, хват, подъём, удержание и нужная осевая ориентация. Сначала известная поза для диагностики |
| G3 — поиск | Варианты позиции/угла предмета, camera-only поиск и оценка, отдельные тестовые размещения; случаи «нет предмета» |
| G4 — применение | После реального sim-хвата повторить нажатия, отпустить клавиши, сравнить режимы tool/jaw; обнаруживать проскальзывание/потерю |
| G5 — последовательность | Поддерживаемое слово, проверка строки и ошибок на новых исходных позах. Фактические contacts/key events, не программный ввод текста в ОС |
| G6 — агент | Вызовы уже принятых операций из готового agent runtime; наблюдение, запуск, завершение/ошибка/повтор |

Роботная операция и checkpoint не обязаны соответствовать друг другу один-к-одному. Одна goal-conditioned policy может нажимать разные клавиши; один VLA/WAM — выполнять несколько манипуляций. Разделяем проверки операций, а количество моделей определяется результатами готового метода.

Объединение мировой desktop layout, выбранной камеры и native typing contact gate из [действующего плана](<../../../../../../_ПЛАНЫ_/embedded-robotics-market-research/research/projects/robohand/plans/2026-11-16-implementation.md>) продолжается. G1–G3 можно исследовать параллельно этой подготовке; сроки обучения хвата не обещаются до G1/G2. Нового исполняемого runtime/controller/adapter этим документом не создано.
